Loss per event is unbounded relative to the action, and the failure is invisible in the transaction record (`research.md:30-34`). | Passport | Higher stakes per incident and a sharper "why now" story. | Niche sharpness | "Technical agent work" spanning audits, implementation, review (`firewall.md:23-26`). Broad by the spec's own admission. | One action class, one target, one selector, declared as a product boundary (`passport.md:15`). | Passport | Passport picks a wedge; Firewall picks a category. Judges reward the wedge when it produces an unambiguous demo. |
| Why persistent memory is necessary | The failure mechanism must survive across providers and sessions so a new provider triggers the same safeguard (`firewall.md:45`). Necessary, but the output is advisory until a client approves. | The causal lesson must survive across executors and sessions so the obligation set changes for a different executor (`passport.md:161`). Necessary, and the output is a hard precondition. | Passport (narrow) | Both are genuinely cross-identity. ## PMF and multiplier
- Actual PMF score for both: 0 / 10 unless public validation is independently supplied.
- PMF potential for each: Firewall has a plausible named audience (clients paying agents for technical work) but no validated demand in the reviewed materials; potential 2–4 with a public pilot, design partner, or waitlist. Passport has a sharply defined treasury-operator audience and a credible failure mode, but no named operator asking for the product; potential 2–4 with one public testnet pilot. Problem plausibility alone earns neither idea a bonus.
- Partner multipliers: not assessed in idea mode.

## Recommendation
- Choose: **Execution Passport**.
- Decision rationale: Both ideas are designed around the gate's required write, fresh-session read, and deletion behavior. The rubric's largest weights are memory (40) and innovation (25), and Passport wins innovation clearly and memory narrowly because its memory output is a hard execution precondition rather than a proposal a client may decline. Firewall wins on build credibility and security risk, but those affect the 20-point technical row, which Passport still scores acceptably on if the verifier stays narrow. The deciding factor is reducibility: Firewall's own spec admits it can be imitated by a database plus templates and that its moat is the loop, while Passport's reducibility risk (a single hypothesis with literal thresholds) is fixable by making the stored hypothesis—not code defaults—the source of obligation selection and thresholds (`research.md:87-99`).
- What should be explicitly dropped to keep the chosen idea focused: `rollback-route` beyond a schema field (already deferred, keep it that way); Safe Guard or AccessManager integration beyond a roadmap note; every action class except `treasury-rebalance`; automated exploit detection or recovery; on-chain verification of the underlying simulation/oracle evidence; and any claim that oracle freshness or simulation makes the rebalance economically safe. Keep `memory_root` and `obligation_results_hash` as commitments, but describe them honestly as signer-bound audit references rather than proofs independently validated by the verifier.

## Strongest objection to the recommended idea
The MVP has one hypothesis, one action class, and a four-item obligation set whose thresholds appear as literals in the spec (`passport.md:90-96`). A judge can argue that memory stores a boolean ("strict mode on") and a static policy engine such as Fireblocks-style rules or a Safe Guard with a config file would behave identically. The design's answer, that memory must change obligation selection, thresholds, enforcement mode, counterfactual, and calibration (`research.md:91-97`), is correct, but the MVP as written only exercises selection and enforcement mode. If the demo does not show thresholds and obligation lists coming out of Sibyl, and does not show an outcome write changing a later decision, the memory score collapses to the low twenties and Firewall, with three patterns and cross-provider retrieval, would have been the better pick. This objection is about realization, not concept, but it is the single largest source of variance in the score.

## The one proof the final demo must show
In one unedited segment with a commit hash on screen: a fresh process under a different executor identity reads the Control Hypothesis from Sibyl, the obligation list and thresholds shown on screen come from that read, the verifier rejects a stale or reused passport for the exact rebalance, a compliant passport executes it exactly once, and after deleting the memory the same request produces "bootstrap: human review required" with no passport issued. If any one of these five beats is missing, the deletion test is not proven.

## Claims that would be misleading or unsupported
- "Execution Passport makes DeFi treasury actions safe." Unsupported; the spec itself lists this as a non-goal (`passport.md:29`).
- "The passport verifier is production Safe infrastructure" or "works with any Safe transaction." Misleading; scope is one mock target and one selector (`passport.md:167-173`).
- "The verifier checks the proof bundle on-chain." Misleading; the contract verifies a signature over a digest and trusts the policy signer (`passport.md:123`).
- "Memory cannot be replaced." Both specs correctly avoid this (`firewall.md:310`), and the review agrees; the honest claim is that removing memory removes the incident-conditioned behavior.
- "Escrow Firewall prevents bad delivery." Overclaim; it changes proposed terms before funding and still depends on client approval and on the evaluator catching the failure (`firewall.md:149, 194`).
- "Escrow Firewall is not a reputation system." Defensible only if the demo shows a different provider triggering the safeguard; without that scene it looks like provider scoring.
- Any PMF claim for either idea. No public validation exists in the reviewed documents.
- Any statement that existing primitives "cannot" do incident-conditioned policy. The defensible statement is that the cited documentation for Safe Guards, AccessManager, Tenderly, and EIP-712 does not describe such a feature.
